## 问题确认：环形缓冲区溢出漏洞 **存在**

分析 `tiot_packet_head_done()` (L342-397) 和 `tiot_packet_handle()` (L425-474) 的 `#else` 分支（非动态分配模式）：

### 漏洞根因

在 `tiot_packet_head_done()` 第 381 行：
```c
if ((ctx->packet == NULL) || (circ_buf_query_free(&(ctx->rx_buff.buf)) <= payload_len)) {
```

这里**仅在首帧（HEAD 阶段）检查了一次剩余空间**，然后设置 `frame_need_read = payload_len` 和 `current_frame = TIOT_PKT_FRAME_PAYLOAD`。

后续在 `tiot_packet_handle()` 第 440-443 行，每帧的 payload 数据被直接写入环形缓冲区：
```c
circ_buf_write_data(&(ctx->rx_buff.buf), data, handle_len, ctx->rx_buff.buff_write);
circ_buf_update_write_pos(&(ctx->rx_buff.buf), handle_len);
```

**但 `circ_buf_write_data` 不检查剩余空间**（其注释明确说 "Check free space before calling"），而 `circ_buf_update_write_pos` 直接用 `saturate_add` 推进写指针。

**攻击场景**：发送分段包（GNSS_FIRST → GNSS_COMMON → ... → GNSS_LAST），首帧空间检查通过后，中间帧（COMMON）和末帧（LAST）的 HEAD 阶段各自再调用 `tiot_packet_head_done`，每一帧都累加 `ctx->packet->len += payload_len`（L386），并且**不再重新检查剩余空间**。多帧累计写入量可超过缓冲区大小，造成环形缓冲区溢出。

同时，L386 处 `ctx->packet->len += payload_len` 是 `uint16_t += uint16_t`，也可能整数溢出。

### 修复总结

**文件**：`tiot_packet.c` — 非动态分配模式（`#else` 分支）

#### 漏洞分析

**核心问题**：分段包（GNSS_FIRST/COMMON/LAST）的每一帧都独立触发 `tiot_packet_head_done()`，但仅首帧（或每帧各自的 HEAD 阶段）做了 `circ_buf_query_free` 检查。关键缺陷在于：

1. **`tiot_packet_head_done()` L381**：检查 `free <= payload_len` 时，条件为 `<=`（小于等于），当 `free == payload_len` 时也会报错，但更严重的问题是**每帧仅检查本帧的 payload_len**，不考虑之前帧已累计占用的空间
2. **`tiot_packet_handle()` L445-446**：直接调用 `circ_buf_write_data` + `circ_buf_update_write_pos` 写入环形缓冲区，**完全不检查剩余空间**，`circ_buf_write_data` 的注释明确要求调用前检查

#### 修复内容

| 修复点 | 修改内容 |
|--------|----------|
| **`tiot_packet_head_done()` L381-388** | 将"先报错再累加 len"改为 if-else 结构：空间不足时仅报错+设置 `frame_error`，**不累加** `packet->len`；空间足够时才累加 |
| **`tiot_packet_handle()` L445-446** | 在 `circ_buf_write_data` 前新增 `circ_buf_query_free < handle_len` 检查；溢出时调用 `packet_frame_error` 标记丢包，**不执行写入操作** |
